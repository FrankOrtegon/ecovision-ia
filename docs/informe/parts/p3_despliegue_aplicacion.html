Despliegue del Modelo

El modelo seleccionado se aloja en la infraestructura de Roboflow y se consume mediante su API de inferencia sin servidor (serverless; Roboflow, s. f.-a). La solicitud es un POST a https://serverless.roboflow.com/{proyecto}/{versión} con la imagen codificada en base64 y la clave de la cuenta en la cabecera Authorization: Bearer; en este proyecto el identificador es ecovision-trashnet/1. Mediante llamadas reales se comprobó que ese identificador resuelve al modelo entrenado ecovision-trashnet-1-resnet50-t1 y que el identificador ecovision-trashnet/2 resuelve al segundo modelo, lo que permitió compararlos sin ambigüedad. La respuesta de clasificación contiene, para cada clase devuelta, su nombre y su confianza, además de la mejor clase.

La verificación empírica del comportamiento del servicio reveló un hecho con consecuencias para la evaluación: aun con el umbral de confianza en cero, la API omite las clases cuya probabilidad es inferior a aproximadamente 1 %. En una imagen de plástico, por ejemplo, devolvió cinco de las seis clases, con una suma de 0,9948, y omitió la clase metal. Como la suma de las probabilidades es conocida, el sistema estima las clases omitidas repartiendo el residuo (1 menos la suma) entre ellas y marca cada respuesta con un indicador de estimación. La exactitud, la precisión, el recall y el F1 no dependen de esta estimación, porque usan la clase de mayor probabilidad; las curvas ROC y PR y sus áreas sí, y por eso se reportan como aproximadas y se acompañan de un análisis de sensibilidad (Tabla 8).

La latencia de la API que informa Roboflow es de milisegundos (3,5 ms en la ficha del modelo 1, tiempo de servidor sin red). Medida de extremo a extremo desde la aplicación, una clasificación individual tarda entre [[lat_min]] y [[lat_max]] ms según la red, y la evaluación de las [[n_test]] imágenes de prueba a través de la aplicación tardó [[seg_eval]] segundos con cuatro solicitudes en paralelo.

Creación de la Aplicación

Arquitectura

La aplicación sigue una arquitectura de tres capas con separación de responsabilidades (Figura 3). El navegador ejecuta una aplicación de una sola página en React que solo se comunica con el backend; el backend, escrito en Python con FastAPI, valida las entradas, orquesta las llamadas al modelo alojado y calcula las métricas con scikit-learn mediante un paquete de evaluación independiente que también usan los scripts del proyecto. La clave de Roboflow existe únicamente en el backend (variable de entorno) y nunca llega al navegador.

Backend y API REST

El backend (Python [[py_ver]], FastAPI [[v_fastapi]], Pydantic [[v_pydantic]]) expone cinco endpoints con contratos tipados y documentación OpenAPI/Swagger generada automáticamente (Tabla 4). Las respuestas de error tienen un formato uniforme con un código y un mensaje en español.

Tabla 4

Endpoints de la API

Método y rutaFunción
GET /api/healthEstado del servicio, si el modelo está configurado y los límites vigentes
GET /api/model/infoInformación del modelo leída de un registro de entrenamiento real
POST /api/predictClasifica una imagen y devuelve las seis probabilidades
POST /api/predict/batchClasifica hasta [[max_batch]] imágenes; un fallo no detiene el resto
POST /api/evaluateRecibe imágenes y un CSV filename,true_label y devuelve todas las métricas

Nota. Documentación interactiva en /docs. Los límites (tamaño máximo de [[max_mb]] MB por imagen, [[max_batch]] imágenes por lote y [[max_eval]] por evaluación) son configurables.

Las entradas se validan en capas: extensión (JPG, JPEG, PNG o WEBP), tamaño, contenido real de la imagen (se abre con Pillow, sin confiar en la extensión), número de píxeles (contra imágenes malformadas de tamaño desproporcionado) y número de archivos. Las imágenes se procesan en memoria y no se almacenan. Se configuraron orígenes CORS explícitos (el modo de producción rechaza comodines), cabeceras de seguridad básicas y tiempos de espera en toda llamada externa, con un único reintento ante errores transitorios del proveedor. El registro de eventos no incluye URLs ni mensajes de excepciones de la biblioteca HTTP, y una prueba automatizada verifica que la clave no aparezca en errores ni en registros. Si el modelo no está configurado, la API responde con un error 503 explícito en lugar de devolver una predicción simulada.

Interfaz de usuario

La interfaz (React [[v_react]], TypeScript [[v_ts]], Vite [[v_vite]], Tailwind CSS [[v_tw]], Recharts [[v_recharts]] y Axios) está íntegramente en español y es responsiva. Tiene cinco módulos, accesibles desde una barra lateral con indicador del estado del servicio:

  • Inicio (Figura 4): descripción, contexto, objetivo, las seis categorías, funcionamiento y acceso al clasificador.
  • Clasificador (Figura 5): carga de una imagen con validación inmediata y vista previa, categoría predicha, porcentaje de confianza, barras con las seis probabilidades y un aviso cuando la confianza es baja (menor de 60 %).
  • Procesamiento por lotes (Figura 6): tabla con archivo, categoría y confianza, estado del procesamiento, lista de archivos fallidos y exportación a CSV.
  • Evaluación (Figura 7): carga de imágenes etiquetadas y un CSV, comprobación previa de coincidencias, y tablas y gráficos con exactitud, precisión, recall y F1 por clase y promedios macro y ponderado, matriz de confusión, curvas ROC con AUC y curvas PR con AP; exportación de métricas y predicciones.
  • Acerca del modelo (Figura 8): datos del modelo, conjunto, configuración, métricas y limitaciones, leídos de la API; los campos sin dato se muestran como Pendiente y nunca se inventan.

El módulo de evaluación responde al requisito de que el usuario cargue conjuntos de datos y obtenga resultados: acepta hasta [[max_eval]] imágenes con su etiqueta real, relaciona cada imagen con su fila del CSV, ejecuta el modelo y calcula las métricas. Para comprobar que la aplicación es fiel al análisis científico, se evaluaron las [[n_test]] imágenes de prueba a través de la interfaz y se obtuvieron los mismos valores que con el script (exactitud [[acc_test]], F1 macro [[f1_macro]], AUC macro [[auc_macro]]).

Calidad, pruebas y reproducibilidad

El proyecto incluye [[n_tests_total]] pruebas automatizadas (Tabla 5). Las del backend usan un clasificador falso solo dentro de las pruebas y un transporte HTTP simulado para el adaptador de Roboflow, de modo que el servicio real nunca contiene una vía simulada. Las pruebas de métricas comparan con valores calculados a mano (por ejemplo, un AUC de 7/8 en un caso mínimo) y verifican que la curva ROC usa probabilidades y no etiquetas predichas, y las de la interfaz cubren validación de archivos, exportación a CSV segura frente a inyección de fórmulas, mapeo de errores y el flujo de clasificación con éxito, error y confianza baja. El código backend pasa el análisis estático con Ruff y el modo estricto de mypy, y el frontend pasa la verificación de tipos y ESLint.

Empaquetado y publicación

El backend se empaqueta en una imagen de Docker con un usuario sin privilegios; la imagen se construyó y se ejecutó localmente en modo producción con la clave real, y se comprobó el estado del servicio, la lectura del registro del modelo, una predicción real, una evaluación con scikit-learn dentro del contenedor y el rechazo de orígenes CORS no permitidos, con un consumo de memoria de unos 148 MiB. El repositorio incluye la configuración para publicar el backend en Render y el frontend en Vercel. Render documenta que los servicios gratuitos se suspenden tras 15 minutos sin tráfico y tardan cerca de un minuto en reactivarse (Render, s. f.), un detalle relevante para una demostración.
